# VDS Frontend Workbench

Phase 9 static frontend plus Phase 10/12 result-experience panels for the backend Data Agent API.

It connects to:

- `POST /api/data-agent/upload`
- `POST /api/data-agent/upload-batch`
- `POST /api/data-agent/message`
- `POST /api/data-agent/benchmark/run`
- `GET /api/data-agent/conversations`
- `GET /api/data-agent/conversations/{conversation_id}`
- `PATCH /api/data-agent/conversations/{conversation_id}`

The frontend only handles upload, message submission, per-turn assistant rendering, chart display from backend `chart`, insight rendering, safe code-card rendering from backend `execution_artifacts`, a user-facing process timeline from backend `process_view_v2`, a right-side activity drawer from backend `activity_trace_v2`, safe monitor-event display, Project selection, and conversation history display. Run history now uses backend `conversation_id` records: page load fetches the conversation list, selecting a history item restores saved user/assistant messages, and rename / pin calls the backend PATCH endpoint. When chart data is available, the workbench renders an interactive frontend SVG with axes and hover value tooltips from the backend `chart` spec; `chart.image_data_uri` remains a static fallback when chart rows or encodings are insufficient. File selection is quiet: the composer shows an attachment chip, but the chat area does not render upload results, profile panels, or upload-error analysis cards. The main shell no longer shows advanced Rule Mode or Benchmark controls. Users can upload dataset files together with `.md/.txt/.yaml/.yml/.doc/.docx/.docm/.rtf/.odt/.pdf/.pages/.html/.htm` knowledge files or rule-like `.json`; backend binds those files as `user_analysis` rules for the dataset. Project home is browse-only until the user explicitly starts a Project chat, resumes a Project conversation, or chooses `移至项目` from a history menu; only those explicit states pass or write `project_id`. Conversation pinning is persisted by backend `pinned / pinned_at`; the frontend only toggles it through PATCH, renders the pin marker, and respects backend ordering in global history and Project home. Pure `.md/.txt/.yaml/.yml/.doc/.docx/.docm/.rtf/.odt/.pdf/.pages/.html/.htm` Project source uploads remain shared project notes and do not replace the active dataset. Benchmark rules remain backend/API-only and run only through `/api/data-agent/benchmark/run`. The browser does not inspect `fees.json`, `merchant_data.json`, `manual.md`, rule contents, formulas, benchmark metadata, or standard answers. When the user sends a question, the composer first calls the upload API if needed, then submits one `/api/data-agent/message` request with the current `conversation_id`, optional `project_id`, and optional `monitor_run_id` when available. Backend routing decides whether the message is ordinary chat, dataset overview, or full analysis. Backend audit details such as quality reports, warnings/errors, verification internals, and join-plan traces remain backend/API data and are not shown in the main user shell. `process_view_v2` and `activity_trace_v2` are safe narrative/activity fields, not raw Chain of Thought; monitor deltas are temporary and final `/message` payload wins. The frontend does not implement metrics, joins, scoring, chart selection, anomaly rules, cleaning logic, DAB rule parsing, user rule parsing, Benchmark parsing, project memory retrieval, process inference, overview report generation, code generation, activity inference, or data calculation.

Run the backend from the repo root, then open `frontend/index.html` through a static server or serve it from the same host as the API.
